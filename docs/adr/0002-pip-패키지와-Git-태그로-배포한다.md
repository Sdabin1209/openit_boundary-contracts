# 0002. 계약을 pip 패키지로 만들어 Git 태그로 배포한다

- 상태: 수용(2026-10-28 소급 기록)
- 관련: D18, D19, D41, D46 / `README.md` 태그 규칙 / `shared/CLAUDE.root.md` 컨테이너 절

## 맥락

13개 리포가 같은 계약을 읽는다. 계약 변경이 소비 영역에 조용히 번지지 않고, 소비 영역이 개발·시험·이미지 빌드에서 정확히 같은 버전을 쓸 수 있어야 한다.

## 결정

이 리포를 `boundary_contracts` 파이썬 패키지로 만든다(스키마가 패키지 안에 들어 있다). 소비 영역은 `pip install git+ssh://...openit_boundary-contracts.git@<태그>`로 설치하고 이미지 빌드 때 태그를 고정한다. 별도 패키지 인덱스 서버를 두지 않는다. 릴리스 태그는 주석 태그이고 한 번 push한 태그를 옮기거나 지우지 않는다.

## 왜

- D18: SDK 배포는 Git 태그 설치로 시작한다(별도 인덱스 서버를 두지 않는다). 운영 대상이 단일 서버 한 대이고(D11) 원격이 모두 비공개 GitHub라 인덱스 서버를 추가로 운영할 이유가 없다.
- 스키마가 패키지에 포함되므로 소비자는 `load_schema`, `validator`로 읽을 수 있고 복사본이 필요 없다. 복사본은 어긋난다(workspace 규칙).
- 태그 고정은 재현성의 기반이다. 게이트가 승인한 동작과 서비스가 같아야 한다(D46, D80). 태그를 옮기지 않는 규칙은 이미 의존한 영역의 잠금 파일이 깨지는 것을 막는다.
- 무결성은 서명이 아니라 잠금 파일의 태그와 커밋 해시로 본다. 서명 키 관리는 사용자 결정이 필요해 하지 않았다(README 태그 규칙).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 모노레포(한 저장소에 모든 영역) | 근거 기록 없음의 부분이 있다. 확인되는 이유: 이 프로젝트는 영역마다 독립 git 리포를 두고 자기 리포 안에서만 일하는 규칙(D02, D04, D28)으로 출발했다. 모노레포는 그 구조의 전제와 맞지 않는다. 모노레포를 직접 비교한 문서는 찾지 못했다 |
| 사설 패키지 레지스트리(PyPI 호환 서버) | D18이 "인덱스 서버를 두지 않음"으로 정했다. 운영할 서버와 인증이 늘어난다. 이유 문장은 D18에 한 줄뿐이며 비교 측정은 없다 |
| 영역마다 스키마를 복사 | 어긋남. 규칙으로 금지 |
| 서비스 형태의 계약 서버(스키마를 HTTP로 제공) | 개발·시험 때 서버가 있어야 하고 오프라인 검증이 불가능해진다. 근거 기록 없음, 추론 |

## 결과

- 얻는 것: 서버 추가 없음, 태그로 정확한 버전 재현, 소비자가 `pip install`만 하면 스키마와 클라이언트가 같이 온다.
- 감수하는 것: 설치에 GitHub SSH 키가 필요하다. 태그가 원격에 push되었는지 확인하지 못했다(README 4절). 문서만 바뀐 main은 태그 없이 두므로 `main`과 최신 태그가 다를 수 있다(CHANGELOG의 'main' 절에 적는다). v1.3.x는 경량 태그라 앞으로 만들지 않는다.

## 되돌리는 조건

리포가 공개되거나 소비자가 외부 팀(프론트 등)으로 늘어 SSH 키 배포가 부담이 되면 레지스트리를 다시 검토한다. 그때에도 태그 불변과 잠금 파일 고정 정책은 유지한다.
