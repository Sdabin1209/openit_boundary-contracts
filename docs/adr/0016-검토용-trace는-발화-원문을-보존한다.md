# 0016 검토용 trace 는 환자 발화 원문을 보존한다 (reviewer 전용)

- 상태: 채택(2026-11-03, 3.2.0)
- 맥락: 비식별 trace(OpsFeedbackDeidentifiedTrace)는 자유 문자열을 전부 마스킹한다(허용 목록 방식, D88 최소 보존). 그 결과 실패 사례에 환자 발화가 없어 검토자가 "실제 결함인지"를 판단할 수 없었고, 확정 사례를 재학습 재료로 쓸 수도 없었다. 검토 고리가 설계상으로만 닫혀 있었다(L12).
- 결정: 사용자 결정(2026-11-03)으로 검토 사본 스키마 `OpsFeedbackReviewTrace` 를 둔다. 비식별 trace 와 같은 모양이되 발화 두 칸(`frontend_message.utterance`, `extract_input.user_utterance`)만 원문(≤1000자, 문진 스키마 UtteranceBody 상한)을 허용한다. I7 에 `GET /v1/review-traces/{ref}` 를 추가하고 reviewer 역할만 읽는다. 읽을 때마다 접근 기록(누가·언제·어느 사례)을 남기고 그 기록은 감사 기록 보존(365일)을 따른다. 사례 자체의 보존은 확정 사례 180일 그대로. 외부 전송 없음. 잔존 패턴(전화·주민번호·이메일) 검사는 보존된 칸에도 적용되어 걸리면 사례를 만들지 않는다. 기존 `get_trace` 는 마스킹된 뷰 그대로다. 정책은 `OpsFeedbackJobConfig.deid.review_utterance{keep,max_chars}` 로 켠다(경로 지정).
- 왜: 검토는 발화를 봐야 가능하다. 자동 PII 탐지 없이도, 원문을 저장소 안에 두고 사람(reviewer)만 접근 통제 아래 보게 하면 성립한다. 문장 속 PII 를 자동으로 찾아 가리는 처리는 한국어 탐지 라이브러리·모델이 필요해 이번 범위 밖이다.
- 검토한 대안: (a) 검토 기능을 제품에서 빼고 집계만 — 사용자가 거부(기능을 빼는 해결 금지). (b) 기존 스키마의 발화 칸을 완화 — 모든 읽기 역할(합성 데이터·model-lab·저작)이 원문을 읽게 되어 버림. (c) 자동 PII 마스킹 뒤 보존 — 탐지기 부재.
- 결과: 가명 정보(발화)가 ops-feedback 저장소에 180일 남는다. 설치 문서에 이를 명시한다. 정책 지문이 바뀌어 기존 PENDING 사례는 재처리되지 않는다. 접근 기록 저장소(aux)의 보존 365일은 사례 180일과 다르게 둔다(감사 기록).
- 되돌리는 조건: 한국어 PII 자동 탐지가 도입되면 보존 칸을 마스킹 후 보존으로 바꾼다. 개인정보 정책이 원문 보존을 금지하면 (a)로 돌아간다.
