# 0009. 비밀은 NAME_FILE로 받고 read_secret(NAME)으로 읽는다

- 상태: 수용(D84, 패키지 2.0.2)
- 관련: D84, D88 / `boundary_contracts/secrets.py` / `CONVENTIONS.md` 6절 / `CHANGELOG.md` 2.0.2

## 맥락

2026-10-27 gpu-dev 측정 중 에이전트가 `docker exec ... env`로 시험용 토큰 5개를 출력에 노출했다. 근본 원인은 구조였다: 모든 서비스가 `env_file`로 토큰을 환경 변수로 받아, 컨테이너에 접근할 수 있는 누구나 `env`/`inspect`로 평문을 읽을 수 있었다(D84).

## 결정

서비스는 `<이름>_FILE`로 받은 경로의 파일에서 비밀을 읽는다. 공유 함수 `boundary_contracts.secrets.read_secret(NAME)`이 `NAME_FILE`을 먼저 읽고, 없으면 환경 변수 `NAME`(개발·시험용)을 쓴다. 오류 메시지에 값을 넣지 않고, `secret_source(NAME)`은 값 없이 출처(`file`|`env`|`unset`)만 말한다. 서버 토큰 목록은 `<이름>_TOKENS_FILE`로 받는다(`HTTP.md`). deploy는 compose `secrets:`로 `/run/secrets/...`에 마운트한다.

## 왜

- 환경 변수는 `env`/`inspect`/프로세스 목록/자식 프로세스 상속/크래시 덤프로 새기 쉽다. 파일은 파일 권한과 마운트 범위로 접근을 제한할 수 있다. 컨테이너 비밀을 파일로 주는 방식은 Docker/Compose secrets가 따르는 관행이다(Docker 문서가 환경 변수 대신 secrets를 권하는 점은 이 세션에서 다시 확인하지 않은 일반 지식이다).
- 공유 패키지에 한 번만 둔 이유: 영역마다 읽기 코드를 따로 만들면 같은 실수가 반복되기 때문이다(CHANGELOG 2.0.2의 이유 문장). 이미 모든 영역이 이 패키지를 태그로 의존한다(ADR 0002).
- 환경 변수 호환을 남긴 이유: 개발·시험을 파일 없이 돌릴 수 있게 하려는 것이다. 운영에서는 쓰지 않는다(`CONVENTIONS.md` 6절).
- 값을 오류 메시지에 넣지 않는 이유: 로그·응답으로 새는 것을 막는다(워크스페이스 규칙: 비밀은 이미지, 리포, 설정 파일, 로그, `/readyz`, 오류 응답에 넣지 않는다).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 환경 변수 유지 + `env` 출력 금지 지침만 | 구조가 그대로라 사람/에이전트 실수에 다시 노출된다. 사용자가 근본 원인을 고치라고 지시했다 |
| 외부 비밀 관리자(Vault 등) | 근거 기록 없음. 운영 정책(발급·회전·보관)은 D-A로 별도 미정이다. 단일 서버 구성(D11)에서 추가 서버를 두는 비용은 검토한 기록이 없다 |
| 영역마다 읽기 코드 | 위 이유(반복되는 실수) |

## 결과

- 얻는 것: 서비스 토큰이 `env`로 보이지 않는다. 읽기 코드가 한 곳이다.
- 감수하는 것: 비밀 발급·회전·보관 정책은 해결되지 않았다(D-A 열림). 파일 권한 설정은 deploy 소관이다. 실제 마운트 경로와 권한은 이 리포에서 확인하지 못했다.

## 되돌리는 조건

외부 비밀 관리자를 도입하면 `read_secret`의 읽기 원천만 바꾸고 호출 모양(이름 → 값)은 유지한다.
