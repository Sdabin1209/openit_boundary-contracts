# 0004. 하위 호환 규칙: ext, MINOR는 추가만, 쓸 때 엄격하고 읽을 때 관대하게

- 상태: 수용(MAJOR 병행 기간은 2.0.0에서 예외로 건너뜀)
- 관련: D25, D26, D42, D43 / `CONVENTIONS.md` 1·3절 / `CHANGELOG.md` 2.0.0

## 맥락

영역은 서로 독립적으로 개발·배포된다. 사용자가 "계약을 매번 뜯어 고치지 않게"를 요구했다(D26). 계약이 바뀔 때 이웃이 한꺼번에 깨지지 않아야 한다.

## 결정

1. 모든 레코드에 선택 필드 `ext`(키는 영역 이름)를 둔다. 읽는 쪽은 이해 못 해도 보존·전달하고 판단에 쓰지 않는다. 여러 영역이 필요로 하면 정식 필드로 올린다(MINOR).
2. MINOR는 추가만 한다(선택 필드, 열거값, 허용 범위 확대). 필수 필드 추가, 삭제, 이름·의미 변경, 범위 축소는 MAJOR다.
3. 쓰는 쪽은 자기 버전의 스키마(`additionalProperties: false`)로 엄격히 검증하고 쓴다. 읽는 쪽은 같은 MAJOR의 모르는 필드를 무시하고 모르는 열거값을 '알 수 없음'으로 처리한다.
4. 모든 레코드는 불변이다(D25). 고치지 않고 새 ID나 새 버전을 만든다.
5. MAJOR를 올릴 때는 이전 MAJOR를 읽는 경로를 한 릴리스 주기 동안 병행한다. **예외: 2.0.0은 병행하지 않았다.**

## 왜

- `ext`: 한 영역의 새 정보가 계약 변경을 거치지 않게 하려는 것이다(D26). 보존·전달 의무가 있어야 `ext`가 중간 영역에서 사라지지 않는다.
- 쓸 때 엄격/읽을 때 관대: 이 원칙은 견고성 원칙(Postel)과 같은 모양이다. 인용 기록은 없다. 쓰는 쪽을 엄격히 하면 불량 데이터가 저장소에 들어가지 않고, 읽는 쪽을 관대하게 하면 MINOR 추가 때 이웃 서비스가 죽지 않는다. 무결성은 해시로 따로 지킨다(내용 해시는 모르는 필드까지 포함한 원본으로 계산, `HTTP.md` 공통).
- 불변: 승인 이력과 해시가 한번 정해지면 바뀌지 않아야 감사가 된다. 그래서 `ModelPackageManifest`에 상태 필드가 없고 승인은 별도 레코드(`GateDecision`)다(D25).
- 병행 예외의 이유(`CONVENTIONS.md` 1-4): v1 계약이 기술하던 단계(파서·정규화기·판정기·Plan)가 없어졌고, 학습된 모델은 v2 형식만 말하며, 운영 데이터가 아직 없는 데모 단계이기 때문이다. v1은 태그 `v1.3.3`으로 남는다. 클라이언트는 MAJOR 1 레코드를 `UNSUPPORTED_VERSION`으로 거부한다.

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 읽는 쪽도 엄격(모르는 필드 거부) | MINOR 추가마다 이웃이 깨진다. D26 요구에 반한다 |
| 확장 필드 없이 필요할 때마다 MINOR | 한 영역의 필요가 계약 변경 절차를 거쳐야 해 느리다 |
| 변경 가능한 레코드 | 해시·감사 의미가 사라진다 |

## 결과

- 얻는 것: 이웃이 동시에 올릴 필요가 없다. 하위 호환 시험이 있다(1.2 변경이 이를 검증했다).
- 감수하는 것: 관대한 읽기는 오류를 늦게 발견하게 할 수 있다. `ext`가 방치되면 정식 필드로의 승격이 늦어진다. 2.0.0 병행 예외는 소비 영역이 한 번에 갈아탄 선례가 되었다.

## 되돌리는 조건

운영 데이터가 쌓인 뒤의 MAJOR 변경에서는 병행 기간 예외를 쓰지 않는다(예외의 근거가 "운영 데이터 없는 데모 단계"이므로). 병행 구현 비용이 크면 그때 결정하고 이 ADR을 갱신한다.
