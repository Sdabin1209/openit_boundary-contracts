# 0012. I2 DatasetStore를 HTTP로 하고 I3의 파일 묶음 형식을 따른다 (D100)

- 상태: 수용(2.1.0)
- 관련: D49, D100 / `HTTP.md` ## I2 / `boundary_contracts/clients/datasets.py`, `conformance/servers.py`

## 맥락

I1·I3~I7·I9는 HTTP로 호출하는데 I2만 SDK Protocol로 남아 HTTP 절·클라이언트·참조 서버가 없었다(`HTTP.md`가 스스로 빈 곳을 적었다). 영역 코드를 서로 가져오지 않으려면(워크스페이스 규칙) 읽는 쪽(model-lab)이 네트워크로 읽어야 하고, 이웃 저장소 볼륨 공유는 금지다(D49).

## 결정

- 경로는 `/v1/datasets…`, I3(`/v1/packages…`)와 대칭: 목록, 버전 목록, 매니페스트, 파일 묶음(tar, GET `…/files`), 단일 파일(`…/files/{path}`, 경로는 퍼센트 인코딩한 한 덩어리), 게시(POST tar: `manifest.json` + `files/<경로>`; 201/200/409).
- 클라이언트 `HttpDatasetStore`(표준 라이브러리만), 참조 서버는 `conformance/servers.py`의 `ReferenceServer`에 I3처럼 같은 구조로 추가.
- 게시 검증(파일 해시, 줄 수, EVAL 시나리오가 학습·검증과 겹치지 않음)을 `check_publish`에 한 번만 구현해 클라이언트와 참조 서버가 공유한다.

## 왜

- D49가 영역 사이 호출은 HTTP라고 정했고 I2만 예외일 이유가 없다. 데이터셋은 수 파일의 묶음이라 I3 어댑터와 같은 모양(tar + 해시 대조)이 가장 적은 새 규칙으로 끝난다. 풀 때의 경로 안전 규칙·크기 상한·원자적 배치를 `_http.py`의 기존 구현이 이미 갖고 있다.
- 파일 하나를 읽는 `open_file`(Protocol에 있음)이 필요해 단일 파일 경로를 따로 둔다. 경로 조각은 URL 한 덩어리로 인코딩하므로 경로 안의 `/`가 라우팅과 섞이지 않는다.
- 검증 규칙을 공유하는 이유: 클라이언트와 서버가 다르게 구현하면 한쪽만 통과하는 데이터셋이 생긴다. 서버 쪽 독립 검증은 테스트에서 클라이언트 검증을 우회해 확인한다.
- `scenario_id` 필드가 있는 줄만 겹침을 본다: 샘플 스키마(`ActionExtractionSample`)가 `scenario_id`를 필수로 갖는 줄만 다룬다는 가정이 아니라 줄에 필드가 없으면 건너뛰는 보수적 구현이다(없는 줄이 겹침을 숨길 수 있다는 위험은 샘플 스키마 검증이 필수 필드로 막는다).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| SDK만 두고 같은 프로세스·볼륨 공유 | D49에 어긋나고 E2E에서 이웃 구현을 이미지에 넣지 못했다 |
| 파일마다 개별 호출만(묶음 없음) | 학습 데이터 수 파일을 받을 때 호출·검증이 늘고 일관된 스냅샷을 보장하기 어렵다 |
| 단일 파일 경로 없이 tar만 | Protocol의 `open_file`을 구현하려면 전체를 받아야 한다 |
| 게시를 JSON 본문(base64) | 큰 파일에 비효율이고 I3 형식과 달라진다 |
| 서버만 검증 | 잘못된 데이터를 올린 뒤에야 실패가 보인다. 클라이언트 사전 검증이 업로드를 아낀다 |

## 결과

- 얻는 것: model-lab ↔ synthetic-data가 다른 영역과 같은 방식으로 이어진다. 계약 MINOR 추가.
- 감수하는 것: synthetic-data가 서버를 구현해야 한다. 크기 상한은 `HttpClientBase`의 기본값(tar 8GiB)을 그대로 쓰며 데이터셋 크기를 측정해 정한 값이 아니다(측정 안 함).

## 되돌리는 조건

model-lab과 synthetic-data가 한 영역으로 합쳐지면 불필요하다.
