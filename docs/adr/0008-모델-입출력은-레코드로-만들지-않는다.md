# 0008. 모델 입출력(ActionExtraction 등)은 레코드가 아니라 모델 형식 그대로 둔다

- 상태: 수용
- 관련: D74, D75, D77, D82, D83 / `CONVENTIONS.md` 10절 / `V2_DRAFT.md` / `CHANGELOG.md` 2.0.0·2.0.1

## 맥락

2.0.0(D74)부터 모델 입출력 네 가지(`ActionExtractionInput`, `ActionExtraction`, `ResponseRequest`, `ResponseText`)가 이 리포의 스키마가 되었다. 다른 경계 레코드는 `pipeline_schema_version`과 `ext`를 가진다.

## 결정

이 네 가지에는 `pipeline_schema_version`과 `ext`를 두지 않고 `additionalProperties: false`로 엄격히 검증한다. 읽는 쪽도 완화하지 않는다. 데이터셋 줄(`ActionExtractionSample`, `ResponseSample`)은 레코드이고 `ext`를 가진다. 모델 키는 `<문항>.<칸>` 또는 `<문항>[<종류>].<칸>` 문법을 쓰고, 문항 저작의 구조 참조인 `SlotRef` 문자열과 구분한다.

## 왜

- 모델은 학습된 형식에서만 의도한 대로 동작한다. 입력 글자는 학습 데이터와 글자 단위로 같아야 하고(D77), 출력에는 모델이 내지 않는 필드를 넣을 수 없다. 모델이 말하는 형식 그대로이므로 버전·확장 필드를 얹을 자리가 없다. 얹으면 학습 형식과 달라진다.
- 모델 출력은 제약 디코딩(xgrammar)으로 스키마에 강제된다. `ext` 같은 열린 필드는 제약을 느슨하게 한다. 엄격하게 두어야 형식 위반이 곧바로 거부된다(`OUTPUT_INVALID`, D75).
- 읽는 쪽도 엄격하게: 관대한 읽기는 알 수 없는 필드를 흘려보내는 규칙인데, 모델 출력에서 모르는 필드가 나왔다면 그것은 호환 문제가 아니라 형식 위반이다.
- 버전은 별도로 관리한다: 모델 입출력 스키마의 버전은 `pipeline_schema_version`(이 리포의 MAJOR.MINOR)이고, 모델 패키지가 학습된 문진 스키마의 정수 버전은 `runtime_contract_version`이다(D75-2).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 모델 입출력도 레코드(버전·ext 포함) | 위 이유(학습 형식과 달라짐). 근거 기록: `CONVENTIONS.md` 10절의 한 문장만 있고 대안 비교 문서는 찾지 못했다 |
| 읽는 쪽은 관대하게 | 형식 위반을 숨긴다. 근거 기록 없음, 추론 |
| 제약 디코딩용 평면 스키마를 따로 낸다 | `V2_DRAFT.md` 10절의 미정 항목이다. 아직 결정되지 않았다(D83은 model-runtime이 요청 스키마를 완화해 대응) |

## 결과

- 얻는 것: 학습 데이터·모델·서빙이 한 스키마를 쓴다. 데이터셋 검증 도구(`tools/validate_dataset_v2.py`)가 학습 데이터와 스키마의 차이를 바로 드러낸다.
- 감수하는 것: 모델 입출력은 MINOR 추가로 진화시키기 어렵다. 필드를 더하려면 재학습이 필요할 수 있다(그 판단은 이 리포가 아니라 학습 담당이다). OPEN_GAPS U14(허용 slot 목록 추가를 위한 `ActionExtractionInput` 변경)가 이 제약과 부딪힌다.

## 되돌리는 조건

모델 형식이 바뀌어 학습을 다시 하게 되면(새 데이터셋 버전) MAJOR 변경으로 새 스키마를 낸다. 평면 스키마 분리 결정이 나면 이 ADR을 갱신한다.
