# 0007. 인터페이스를 Protocol로 쓰고, 원격 클라이언트와 참조 서버를 함께 낸다 (메모리 구현은 소유 영역)

- 상태: 수용. 단, 메모리 구현의 소유는 아래 "현재 사실"을 보라
- 관련: D05, D22, D49 / `CONVENTIONS.md` 7절 / `boundary_contracts/sdk.py`, `clients/`, `conformance/servers.py`

## 맥락

영역은 이웃을 블랙박스로 보고 혼자 시험할 수 있어야 한다(`shared/CLAUDE.root.md`: 이웃이 필요하면 메모리 구현으로 대신). 동시에 실제 서비스를 부를 때는 HTTP 클라이언트가 필요하고, 서버 구현은 소유 영역이 맡는다(D49).

## 결정

- `sdk.py`: I1~I7의 `typing.Protocol`. 모든 함수는 실패 시 `BoundaryError`를 던진다.
- `clients/`: HTTP 원격 구현(표준 라이브러리만). 응답을 읽기 모드로 검증하고 해시를 다시 계산한다.
- `conformance/servers.py`: `HTTP.md`대로 응답하는 참조 서버(패키지에는 들어가지 않는다). 소비 영역이 클라이언트를 시험하고 소유 영역이 서버 적합성을 확인하는 기준이다.
- 규약(`CONVENTIONS.md` 7절)은 SDK마다 Protocol, 실제 구현, 같은 오류·멱등성·해시 검증을 지키는 메모리 구현을 함께 내라고 한다. 실제 구현과 메모리 구현은 같은 적합성 시험을 통과해야 한다. 생성자는 설정을 인자로만 받고 환경 변수는 서비스 진입점이 읽는다.

현재 사실(확인): 이 패키지에는 메모리 구현이 없다. `sdk.py` 머리말이 "메모리 구현은 소유 영역이 낸다"고 쓴다. 따라서 "메모리 구현과 원격 구현을 함께 제공"은 규약상의 요구이고, 이 리포가 직접 내는 것은 Protocol, 원격 클라이언트, 참조 서버다. 영역별 메모리 구현이 실제로 규약대로 있는지는 이 리포에서 확인하지 못했다.

## 왜

- 메모리 구현이 있어야 이웃 영역 없이 혼자 시험할 수 있다(D22와 워크스페이스 규칙). 같은 적합성 시험을 통과하게 해 메모리와 실제의 동작 차이를 막는다.
- 클라이언트를 한 곳에서 구현하는 이유: D49의 근거다. 소비 이미지에 이웃 클라이언트를 넣을 방법이 없어 서비스끼리 이어지지 않았던 E2E 막힘이 계기였다. 해시 재검증과 tar 안전 처리를 영역마다 구현하면 어긋난다.
- 클라이언트를 표준 라이브러리만으로 만든 이유: 소비 이미지에 의존 추가 부담을 주지 않으려는 것으로 읽힌다(D49에 "표준 라이브러리만"이라고만 쓰여 있고 이유 문장은 없다. 근거 기록 없음, 추정).
- 서버는 소유 영역이 맡는다: 저장소 쓰기 권한은 소유 영역 하나에만 있다(경계 규칙 1, `CONVENTIONS.md` 6절).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 영역마다 HTTP 클라이언트를 직접 구현 | 해시·tar·오류 처리가 어긋난다(D49). 실제로 E2E에서 영역들이 이어지지 않았다 |
| 이웃의 저장소 볼륨 공유 | D49·D50이 금지. 소유 경계가 무너진다 |
| 이 패키지가 메모리 구현도 소유 | 근거 기록 없음. 소유 영역이 저장 방식을 가장 잘 알아 메모리 구현을 맞추는 쪽이 낫다는 추정은 가능하나 문서에 이유가 없다 |

## 결과

- 얻는 것: 서비스 간 호출이 한 코드로 일관된다. 참조 서버가 `HTTP.md`를 코드로 고정한다.
- 감수하는 것: 참조 서버와 실제 서버의 적합성은 각 영역이 돌려야 하고 이 리포는 확인하지 않는다(README 4절). I2는 클라이언트와 참조 서버가 없다.

## 되돌리는 조건

메모리 구현이 영역마다 어긋나는 사례가 생기면 공통 메모리 구현을 이 패키지로 올리는 것을 검토한다.
