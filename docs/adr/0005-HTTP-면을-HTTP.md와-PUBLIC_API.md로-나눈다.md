# 0005. HTTP 면을 HTTP.md(영역 사이)와 PUBLIC_API.md(화면과 문진 서비스)로 나눈다

- 상태: 수용
- 관련: D12, D49, D55, D58, D64, D65, D66 / `HTTP.md` / `PUBLIC_API.md` / `INTERFACES.md`

## 맥락

영역 사이 호출은 D49로 HTTP가 되었다. 한편 키오스크 프론트는 다른 팀 담당이거나(D12) 떼어 낼 수 있는 별도 영역(D65)이고, 직원 콘솔·운영 콘솔도 있다. 같은 규약 문서에 섞으면 읽는 사람과 변경 속도가 다르다.

## 결정

- `HTTP.md`: 서비스 사이 호출(I1, I3~I7, I9). 서버는 소유 영역, 클라이언트는 `boundary_contracts.clients`가 한 번 구현한다(D49).
- `PUBLIC_API.md`: 프론트(키오스크, 직원 콘솔)와 survey-service 사이(I10). 독자는 프론트 개발자이고 정본이다(HTTP 층의 보충 규칙 `CONVENTIONS.md` 9절은 공개 API 표를 정본으로 둔다).
- 공통 규약(오류 코드, 인증, 멱등성)은 `CONVENTIONS.md`에 한 번만 쓴다.

## 왜

- 독자가 다르다: `PUBLIC_API.md` 머리말이 "독자: 프론트 개발자"라고 밝힌다. 프론트는 이 API만 호출하고 서비스 내부 계약을 알 필요가 없다(D55).
- 변경 주기와 상대가 다르다: 공개 API는 프론트 요청(CR)으로 자주 바뀐다(D66, CR-014·016 등). 영역 사이 규약은 더 안정적이어야 한다. 파일을 나누면 변경 이력과 호환 판단이 섞이지 않는다.
- 의미가 다르다: 영역 사이 호출은 서비스 토큰과 역할, 공개 API는 기기 토큰·사람 인증(`X-Openit-User`, D85·D88)이다.
- 클라이언트 구현의 중복을 없앤다: 서비스 간 호출은 한 곳(`clients`)에서만 구현해 해시 재검증과 tar 안전 처리를 모든 영역이 같게 한다(D49).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 한 문서 | 위 이유(독자, 변경 주기). 근거 기록 없음의 부분: 파일을 합쳐 본 기록은 없다. 분리는 D55 때 `PUBLIC_API.md`를 새로 만들며 시작됐다 |
| 영역별 API 문서를 각 영역 리포에 | 계약 정본이 흩어져 소비자가 블랙박스로 읽을 수 없다(D27) |
| gRPC | 근거 기록 없음. D49는 HTTP로 정했고 gRPC를 비교한 기록을 찾지 못했다 |

## 결과

- 얻는 것: 프론트에게는 한 문서만 주면 된다. 서비스 사이 변경은 프론트와 무관하다.
- 감수하는 것: 공통 규칙이 `CONVENTIONS.md`, `HTTP.md`, `PUBLIC_API.md`에 걸쳐 있어 어긋날 수 있다(401/403 정리 때 실제로 문서 정정이 필요했다, CHANGELOG main 절). I2는 HTTP 절이 없다(HTTP.md에 부재 사유가 있다).

## 되돌리는 조건

프론트가 사라지거나 공개 API를 외부에 공개하게 되면 OpenAPI 문서 생성 등 별도 형식을 검토한다(ADR 0001 되돌리는 조건).
