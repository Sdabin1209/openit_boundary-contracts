# 0003. 버전 규칙: 패키지 MAJOR.MINOR = pipeline_schema_version, PATCH는 스키마 의미 불변

- 상태: 수용
- 관련: D14, D26, D42, D43, D51, D75 / `CONVENTIONS.md` 1·10절 / `CHANGELOG.md`

## 맥락

문진 스키마는 정수 버전(`CONTRACT_VERSION`, 정확 일치)을 쓴다. 영역 사이 계약은 새 필드가 자주 붙을 것이고 읽는 쪽이 필요 이상으로 막히면 안 된다. 두 버전 체계가 헷갈리지 않아야 한다.

## 결정

- 경계 계약 버전은 `MAJOR.MINOR`이고 레코드의 `pipeline_schema_version`에 적는다. 패키지 버전의 MAJOR.MINOR가 이 값과 같고, PATCH는 스키마 의미를 바꾸지 않는 변경(문서, 예시, 순서 정리, 공통 코드 추가 등)이다.
- 문진 스키마의 정수 버전은 `runtime_contract_version`이라는 별도 필드이고 소유는 survey-service다. 둘은 서로 독립이다(`CONVENTIONS.md` 10절).
- 같은 MAJOR이고 MINOR가 더 높은 레코드는 읽기를 허용한다(D14).
- 릴리스 매니페스트는 두 버전을 모두 기록한다.

## 왜

- 소비자가 받아들일 범위를 단순한 규칙으로 판단할 수 있다: MAJOR가 다르면 거부(`UNSUPPORTED_VERSION`), 같으면 읽는다. 이 모양은 널리 쓰이는 MAJOR.MINOR.PATCH 관행(SemVer)을 따랐다. 단 SemVer 문서를 인용한 기록은 없다.
- 두 번째 체계(정수)를 합치지 않은 이유: 문진 스키마는 survey-service가 소유하고(D19, D21) 그 정수는 학습된 모델과 정확히 맞아야 한다(D75-2). 계약 쪽 MAJOR.MINOR는 필드 추가를 허용하는 느슨한 체계다. 요구가 달라 합치지 않았다.
- PATCH를 스키마 의미 불변으로 한정하면 소비자가 자유롭게 올릴 수 있다. 예: 2.0.1은 `ActionExtraction`의 `properties` 순서만 사전순으로 바꿨다(검증 의미 불변, xgrammar가 순서대로 키를 내므로 학습 출력이 막히는 문제를 고침). 2.0.2는 `read_secret` 코드 추가.

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 정수 하나(문진 스키마처럼) | 정확 일치만 허용하면 필드 하나 추가에도 모든 영역이 동시에 올라야 한다. D26의 요구("계약을 매번 뜯어 고치지 않게")와 어긋난다 |
| 날짜 버전 | 호환 여부를 버전에서 읽을 수 없다. 근거 기록 없음, 추론 |
| 패키지 버전과 스키마 버전을 분리 | 두 값을 맞추는 부담. 지금은 MAJOR.MINOR가 같아 소비자가 하나만 보면 된다(근거: `CHANGELOG.md` 머리말). 분리를 검토한 기록은 없다 |

## 결과

- 한계: 2.0.0은 의미가 크게 바뀌어 MAJOR였지만 병행 기간 없이 v1을 폐기했다(ADR 0004).
- 한계: 문진 스키마 정수 1 안에서 비호환 변경이 있었다(OPEN_GAPS G11, TraceEnvelope.trace). 두 체계가 서로 독립이라 생긴 구멍이며 진행 중이다.

## 되돌리는 조건

두 체계를 하나로 합치자는 결정이 나오면(문진 스키마 소유가 헤드로 옮겨지는 경우 등) 이 ADR을 `Supersedes`로 잇는다.
