# 0006. 쓰기 멱등성과 오류 코드(BoundaryError) 체계

- 상태: 수용
- 관련: D16, D25, D58, D66, D75, D86, D87 / `CONVENTIONS.md` 3·4·9절 / `HTTP.md` / `PUBLIC_API.md`

## 맥락

영역 사이 호출은 네트워크를 지나 실패하고 재시도된다. 호출자가 실패 때 무엇을 해야 하는지 모든 영역에서 같은 규칙으로 정해져야 한다. Trace 전달은 최소 1회라(D16) 중복이 반드시 생긴다.

## 결정

1. 쓰기는 멱등이다: 같은 ID(또는 ID+버전)와 같은 내용(같은 `content_hash`)이면 성공이고 기존 것을 돌려준다. 같은 ID에 다른 내용이면 `CONFLICT`다.
2. 모든 경계 호출의 실패는 `BoundaryError(code, retryable)` 하나다. code 8종: `NOT_FOUND`, `INVALID_RECORD`, `UNSUPPORTED_VERSION`, `CONFLICT`, `INTEGRITY_ERROR`, `FAILED_PRECONDITION`, `PERMISSION_DENIED`, `UNAVAILABLE`. 호출자는 `code`와 `retryable`로만 행동한다.
3. HTTP 상태 코드로의 대응은 고정이다(400, 403, 404, 409, 412, 422, 503). 401은 토큰 없음·틀림, 403은 권한 없음이며 둘 다 `PERMISSION_DENIED`다. 429는 `UNAVAILABLE`과 `Retry-After`.
4. `retryable`은 `code`별 기본값이고, 같은 code 안의 예외는 `details.reason`(대문자 코드)으로 구분한다. 예: 409 `CONFLICT`+`TURN_IN_PROGRESS`는 `Retry-After` 뒤 재시도, 503 `UNAVAILABLE`+`OUTPUT_INVALID`(D75).
5. gateway의 상류 장애 응답(503/504, `UPSTREAM_UNAVAILABLE`)은 `BoundaryError`가 아니다. 클라이언트는 502·503·504를 재시도 가능한 일시 장애로 본다.

## 왜

- 재시도를 안전하게 만드는 것이 멱등성이다. 호출자는 `UNAVAILABLE`일 때만 재시도하면 되고, 재시도해도 결과가 같다는 것이 1번 규칙으로 보장된다. 최소 1회 전달(D16)이 중복 제거를 수집 쪽에 맡기는 것과 같은 원리다.
- 코드를 몇 개로 고정한 이유: 호출자가 상태 코드와 메시지 문자열을 해석하지 않고 행동을 정하게 하려는 것이다. 사유를 새 code로 늘리지 않고 `details.reason`으로 구분하면 열거가 커지지 않고(MINOR 추가 부담이 없다) 계약 스키마 변경 없이 사유를 더할 수 있다(D86은 스키마 변경 없이 `TURN_IN_PROGRESS`를 정했다).
- `PERMISSION_DENIED`가 401과 403을 모두 담는 이유: 기존 code를 늘리지 않고 상태 코드로 분기하게 했다(D58, D66: 클라이언트는 상태 코드로 분기한다).
- 이 체계가 gRPC 상태 코드나 HTTP Problem Details(RFC 9457) 등 표준을 따랐는지: 근거 기록 없음. 코드 이름의 일부(`NOT_FOUND`, `FAILED_PRECONDITION`, `UNAVAILABLE`, `PERMISSION_DENIED`)는 gRPC 상태 코드와 이름이 같지만 이를 근거로 적은 문서는 찾지 못했다(추정이며 확정이 아니다).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| HTTP 상태 코드만 사용(본문 없음) | 같은 상태 코드의 세부 사유(409 두 가지 등)를 기계가 구분할 수 없다 |
| 영역마다 자체 오류 형식 | 호출자가 영역마다 다른 분기를 가져야 한다 |
| 재시도 판단을 호출자에게 맡김 | 멱등성 보장 없이는 안전하지 않다 |

## 결과

- 얻는 것: 메모리 구현과 원격 구현이 같은 예외를 같은 조건에서 던질 수 있다(`CONVENTIONS.md` 7절). 참조 서버·클라이언트 적합성 시험이 있다.
- 감수하는 것: gateway 응답이 `BoundaryError` 열거 밖이라 예외 규칙이 따로 있다. 현재 SDK 클라이언트는 `Retry-After`를 읽지 않는다(호출자가 정함, 후속 MINOR 후보).

## 되돌리는 조건

호출자가 더 세밀한 재시도 정책을 요구하거나 `details.reason` 값이 늘어 코드 체계가 불충분하면 새 code(MINOR 열거 추가)를 검토한다.
