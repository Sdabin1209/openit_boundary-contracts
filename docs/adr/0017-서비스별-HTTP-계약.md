# 서비스별 HTTP 계약과 재사용 가능한 데이터 정의

## 상태
채택: 서비스별 계약 분리와 참조 기반 검증. JSON Schema 완전 대체 여부는 미정.

## 맥락
서비스가 다른데 경로가 같은 엔드포인트를 한 OpenAPI paths 객체에 합치면 한 정의가 사라진다.
코드에서 계약을 생성하면 구현의 누락도 계약으로 승인된다. 문서에만 있던 인증·쿼리·상태 조건은 검토와 자동 검증이 어려웠다.

## 결정
서비스별 OpenAPI 3.1 문서와 catalog를 계약 패키지에 배포한다.
공통 데이터는 Draft 2020-12 JSON Schema를 참조하고, 문진 소유자의 데이터는 설치된 소유자 패키지에서 해석한다.
역할·한도 등 환경에 따른 값은 타입이 정해진 wiring 바인딩으로 전달한다.
요청·응답 생산 경계에서 계약을 검사하고 구현 경로와 선언 경로를 별도로 대조한다.

## 왜
OpenAPI 3.1은 JSON Schema 2020-12 기반이다([표준](https://spec.openapis.org/oas/v3.1.0.html)).
동일한 데이터 정의를 복사하지 않고 HTTP 전송 조건과 연결할 수 있다.
jsonschema의 referencing.Registry는 공유된 mutable RefResolver 대신 불변 리소스 레지스트리를 제공한다.
알려진 소유자만 연결해 외부 네트워크 해석과 저장소 구조 결합을 막는다.

## 검토한 대안
단일 paths 병합은 서비스 구분을 잃는다. 코드 기반 생성은 구현과 계약의 독립 검토를 잃는다.
데이터 스키마 복사는 서로 다른 정의가 생긴다. 모든 JSON Schema의 OpenAPI 이전은 내부·배포 계약까지 검토하기 전 확정하지 않는다.

## 결과
패키지에 HTTP 계약과 검사기가 추가된다. 상태 전이·값 간 관계·스트리밍 전송의 업무 조건은 별도 검토가 남는다.
전체 통신의 완결성을 이 문서나 HTTP 경로 대조만으로 주장하지 않는다.

## 되돌리는 조건
소유자 독립성과 데이터 정의의 단일 원본을 유지하는 대체 표준·구성이 검증되면 새 ADR로 대체한다.
